Cmdbar — Command-Surface Design Guide

A unified ribbon + toolbar + menu system for a C# / XAML terminal UI framework · WPF- & Avalonia-compatible · Tokyo Night · whole-cell rendering · v1.0 draft

This guide specifies a single command-surface package for a C# terminal UI framework with full XAML support, modelled on WPF and Avalonia — the cell-grid analogue of Actipro’s Bars for Avalonia. Its central idea is that a Ribbon, a Toolbar, and Menus are not three separate controls but three surfaces over one shared set of bar controls, all driven by the standard ICommand binding model. Build the control set once; each surface is a different XAML arrangement of the same parts, bound to the same commands. Everything below is whole-cell (no sub-cell borders, no smooth gradients) and ships in paired dark/light themes from one ResourceDictionary.

1Architecture — one control set, three surfaces

The package is layered, mirroring WPF/Avalonia conventions. At the bottom is a vocabulary of bar controls — Control-derived elements with attached properties — buttons, toggles, split buttons, popup buttons, comboboxes, galleries, separators. Above that sit three host surfaces that arrange those controls differently, each an ItemsControl:

             ┌──────────────┬──────────────┬──────────────┐
    surfaces │   Toolbar    │    Ribbon    │    Menus     │   ItemsControl hosts;
             │ one row +    │ tabs × groups│ menu bar +   │   arrange controls
             │ » overflow   │ + backstage  │ context menus│
             └──────┬───────┴──────┬───────┴──────┬───────┘
                    └──────────────┼──────────────┘
             ┌──────────────────────────────────────────────┐
    controls │ BarButton  BarToggleButton  BarSplitButton     │   Control-derived,
             │ BarPopupButton  BarComboBox  BarGallery       │   XAML elements
             │ BarSeparator  BarLabel                        │
             └──────────────────────────────────────────────┘
             ┌──────────────────────────────────────────────┐
    command  │ ICommand / RoutedUICommand · CanExecute ·     │   standard WPF/Avalonia
    model    │   Execute · Text · InputGestures · icon     │   commanding; bound once
             └──────────────────────────────────────────────┘

The payoff is reuse through standard commanding: a Bold RoutedUICommand is defined once and bound — via Command="{x:Static …}" — to a ribbon toggle, a toolbar toggle, and a menu item simultaneously. All three share the command’s Text, input gesture (Ctrl+B), and CanExecute/checked state, because they bind the same command object to the same control type. This is exactly how Bars unifies its ribbon and toolbar, and it is idiomatic WPF/Avalonia — no custom plumbing.

DESIGN PRINCIPLE
A surface is a layout strategy, not a new control library. If you find yourself building a “ribbon button” that differs from a “toolbar button,” stop — the difference belongs in the host’s arrangement, not in a forked control.

2Design tokens & the whole-cell contract

Every surface draws from one token set, themed dark/light. These are ResourceDictionary entries — brushes keyed by structural role, not raw colour — referenced with {DynamicResource} so a single dictionary swap re-skins all three surfaces live. (Shown here as the underlying CSS variables; in the framework each is a keyed brush such as CmdToolbarBrush, CmdAccentBrush.)

The whole-cell contract

Command surfaces are dense, so the rendering rules matter more here than anywhere. Three hard constraints:

  • Every control occupies an integer number of cells; widths are reasoned in cells, never pixels. Overflow and reflow are discrete, control-at-a-time decisions.
  • No sub-cell structure: separators are a real │ glyph cell, not a hairline; state is shown by whole-cell fill or foreground, never a 1px border or focus ring.
  • The dropdown arrow on a split button is the one sanctioned exception to “separators cost a cell”: it lives in its own tinted cell (see §3), which carries the two-zone meaning without a separator glyph.
⚠ COMMON FAILURE
Fluid, pixel-by-pixel resize (the ribbon’s signature on the desktop) has no cell analogue. Don’t emulate it with fractional widths — express it as 2–3 discrete density tiers and a clean collapse-to-overflow. The grid’s strength is exactness; lean into it.

3The shared bar-control taxonomy

These are the parts every surface composes. Each is shown here in its toolbar form; the same control re-skins into a ribbon group or a menu row unchanged.

Button · Toggle

Paste│BIU
A button runs a command (one hit target). A toggle is a button with a checked state — checked = accent whole-cell fill (Bold, above). No borders; the fill is the state.

SplitButton — the two-target control

Paste▾│Align▾
A split button (Paste) has two hit zones: the label runs the default action, the ▾ zone opens a menu. The arrow sits in a tinted cell — no separator — so it reads as independently clickable. A popup button (Align) is one target: the whole control opens its menu, marked by a bare caret. This distinction is the subject of a dedicated study; the tinted-zone solution is the resolved convention.

ComboBox / Gallery

Cascadia▾13▾
A combobox is a gallery in disguise: it drops a menu-gallery of choices (with live preview on the focused row). In a ribbon the same gallery can expand into a multi-row in-place grid; in a toolbar it stays a dropdown.

Separator

CutCopy│FindReplace
A single │ cell dividing related clusters. It is the only load-bearing separator; split buttons no longer need one (the tinted arrow zone replaced it).

4Surface A — the Toolbar

The toolbar is a single row of bar controls with computed discrete overflow: it packs controls left-to-right and pockets whatever doesn’t fit into a » popup. This is the cell-grid replacement for the ribbon’s fluid resize — no interpolation, just a measured decision about which controls fit. It costs exactly one row, which is why it’s the right default for most TUI apps.

Overflowed controls keep their identity in the » menu: split/popup buttons show a submenu arrow, comboboxes show value + caret, toggles show on/off state, buttons show their accelerator. The toolbar stays fully usable at any width without reflowing its content.

OVERFLOW ALGORITHM
Pack each control’s cell-width left-to-right while the running total stays under width − 3 (reserving the » cell); the remainder overflows. Trim trailing separators from the visible row and leading separators from the popup so neither ends on a stray │.

STRUCTURE
The Backstage is its own surface, but built from the same parts: the rail is a vertical list of BarButtons (destinations), and each detail pane is an ordinary panel of controls — tiles are large buttons, the recents list is a selectable list, and forms use BarComboBox/fields. In XAML: <cmd:Backstage> with <cmd:BackstageItem Header="Export"> children, each wrapping its pane content.

The ribbon’s additional concepts, all built from the same controls:

  • Tabs & groups — commands cluster into named groups (Clipboard, Style, Inline, Paragraph, Insert), each group a row of bar controls with a label beneath.
  • Contextual tabs — a tab group that appears only when relevant (a table, an image), tinted with --ctx so it reads as conditional.
  • Backstage — the File menu expands to the full-window view shown above: a rail of document-level destinations (New, Open, Save, Export, Print, Account, Options) over a per-destination detail pane.
  • Density tiers — as width shrinks, groups step from large icon-over-label buttons → small inline buttons → a single collapsed group dropdown. Three discrete tiers, not a fluid slide.
  • QAT — a Quick Access Toolbar above/below the ribbon is literally Surface A embedded in Surface B: a mini toolbar of pinned commands. Same control set, nested.
⚠ COST
A classic ribbon eats ~15–17% of an 80×24 terminal before any content. Offer it, but don’t default to it — and make the minimized ribbon (tabs only, band drops on click) a first-class state, not an afterthought.

6Cross-cutting conventions

These apply to every surface because they belong to the shared layer, not any one host.

KeyTips — keyboard access overlay

Pressing Alt overlays each control with a key letter; typing it activates the control or drills into a group. The same mechanism serves the ribbon, the toolbar, and the menu bar — one accelerator model.

Paste│BIAlign▾
Alt-mode: each control shows its KeyTip letter in amber.

SuperTip — rich hover help

Hovering any control (in any surface) can show a titled, multi-line tip with the command name, its accelerator, and a description — richer than a one-line tooltip. Bound to the command, so it’s identical wherever the command appears.

Menus & galleries

Dropdowns from split/popup buttons, the menu bar, and context menus all use one menu primitive: rows with optional icon, label, accelerator, submenu arrow, and check state. A gallery is a menu that lays its items out as a grid (swatches, styles) with live preview — usable as a ribbon in-place grid or a dropdown.

State & theming

  • Hover = whole-cell --btn-hover fill on button-like targets; foreground brighten on text-like ones.
  • Checked/active = --accent fill (toggles, active tab).
  • Disabled = --muted foreground, no fill.
  • Dark/light = one token swap; all surfaces follow.

7API — one command model, two XAML hosts

Here is the shape that makes the architecture real, in the framework’s actual idiom. Commands are defined once in C#, then bound from XAML into whichever surface(s) host them. Because everything is standard ICommand commanding, the same command drives a toolbar button and a ribbon toggle with no per-surface code.

1 · Define commands once (C#)

Use RoutedUICommand for app-wide verbs (they carry Text and InputGestures for free), or a RelayCommand on a view-model for MVVM. Either implements ICommand, so the surfaces don’t care which you choose.

public static class FormatCommands
{
    // RoutedUICommand carries display text + gesture; CanExecute/Execute
    // are wired with CommandBindings on the editor control.
    public static readonly RoutedUICommand Bold =
        new("Bold", "Bold", typeof(FormatCommands),
            new InputGestureCollection { new KeyGesture(Key.B, ModifierKeys.Control) });

    public static readonly RoutedUICommand Italic = /* Ctrl+I */  new("Italic", "Italic", typeof(FormatCommands));
    public static readonly RoutedUICommand Paste  = ApplicationCommands.Paste;
}

// CanExecute / checked-state live in one place; every surface reflects it.
CommandBindings.Add(new CommandBinding(FormatCommands.Bold,
    (s, e) => Editor.ToggleBold(),
    (s, e) => e.CanExecute = Editor.HasSelection));

2 · Surface A — the Toolbar (XAML)

One row of bar controls, bound by Command="{x:Static …}". The host sets OverflowMode; toggles bind their checked state to the command target.

<cmd:Toolbar OverflowMode="CollapseTail">
    <cmd:BarButton       Command="{x:Static cmd:FormatCommands.Paste}" />
    <cmd:BarSplitButton  Command="{x:Static ApplicationCommands.Copy}"
                        MenuItemsSource="{Binding CopyVariants}" />
    <cmd:BarSeparator />
    <cmd:BarComboBox    ItemsSource="{Binding Fonts}"
                        SelectedItem="{Binding FontFamily}" />
    <cmd:BarSeparator />
    <cmd:BarToggleButton Command="{x:Static cmd:FormatCommands.Bold}"   Content="B" />
    <cmd:BarToggleButton Command="{x:Static cmd:FormatCommands.Italic}" Content="I" />
</cmd:Toolbar>

3 · Surface B — the Ribbon (XAML)

The same commands, arranged into tabs and groups. Note FormatCommands.Bold appears here exactly as it did in the toolbar — identical binding, identical text/gesture/checked-state, zero duplicated logic.

<cmd:Ribbon>
  <cmd:RibbonTab Header="Format">
    <cmd:RibbonGroup Header="Clipboard">
      <cmd:BarSplitButton Command="{x:Static ApplicationCommands.Paste}" Size="Large" />
    </cmd:RibbonGroup>
    <cmd:RibbonGroup Header="Inline">
      <cmd:BarToggleButton Command="{x:Static cmd:FormatCommands.Bold}"   Content="B" />
      <cmd:BarToggleButton Command="{x:Static cmd:FormatCommands.Italic}" Content="I" />
    </cmd:RibbonGroup>
    <!-- contextual tabs, backstage, QAT declared the same way -->
  </cmd:RibbonTab>
</cmd:Ribbon>

BarToggleButton bound to FormatCommands.Bold appears in both markup blocks verbatim. The control element (how it’s shown) is chosen per surface; the command (what it does, its enabled and checked state) is shared through {x:Static}. That single fact — idiomatic WPF/Avalonia commanding — is the whole package.

XAML COMPATIBILITY
Controls derive from Control and expose dependency/styled properties, so they participate in normal XAML: Style, DataTemplate, Binding, triggers, and ResourceDictionary theming. The same markup compiles against the WPF-style and Avalonia-style backends; only the namespace URI differs.

Recommendation: default to the Toolbar (+ a menu bar for the long tail), and offer the Ribbon as an opt-in skin for command-dense applications. Because all three are the same controls underneath, switching a surface is a host change, not a rewrite — an app can even let the user choose.

This guide unifies the ribbon and toolbar mockups into one specification for the C# / XAML framework. Both surfaces, the shared Control-derived control set, the ICommand binding model, the overflow algorithm, the split-vs-dropdown convention, KeyTips/SuperTips, and the ResourceDictionary-based dark/light theming are drawn from the same whole-cell design language used across the rest of the component suite, and compile against both the WPF-style and Avalonia-style backends.
