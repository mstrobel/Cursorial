tokyo-night — tag editor anatomy & autocompletion
Full anatomy of the tag/token editor: every sub-component — the chip, its remove affordance, the input/caret zone, and the container — in each interaction state, plus the completion popup’s full lifecycle and an extensible provider model for autocompletion. All whole-cell, both themes; same token system as the rest of the suite.

▸ The chip — every interaction state

Double-click / F2 to edit in place. Chip becomes a tiny inline field with a caret; Enter commits, Esc reverts.

Failed a validator (e.g. not a valid email). Red fill + ⚠; stays editable for correction.

Whole control disabled — greyed, ✕ inert.
read-only
design
Value shown but not removable: no ✕, muted text. For display-only token lists.
The chip is the atom of the control. Its states form a clear ladder from passive to active: normal → hover → focused → editing, plus the error family (duplicate, invalid) and the access modes (disabled, read-only). Each is a whole-cell fill change — no borders. Keyboard focus is distinct from hover so the control is fully navigable without a pointer.

▸ The remove affordance (✕)

rest
tag✕
✕ in --muted — present but recessive, so a row of chips isn’t noisy.
hover ✕
tag✕
Hovering the ✕ itself turns it red — the destructive target is unambiguous before the click.
focused chip
tag✕
When the chip holds keyboard focus the ✕ brightens to --text; Del/Backspace triggers it.
confirm (optional)
tag✕?
For high-value tokens, a two-step remove: first click arms (✕?), second confirms. Optional per-field.
The ✕ is recessive at rest (muted) so a dense row isn’t noisy, but resolves to an unambiguous red destructive target the moment it’s hovered or its chip is focused. An optional two-step ✕? arm-then-confirm guards high-value tokens.

▸ Autocompletion — extensible provider model

The proposal: the popup is not hardwired to a list. A CompletionEngine fans the query out to any number of registered sources, each yielding a uniform CompletionItem[]; the engine debounces, cancels stale requests, merges, ranks, de-dupes, and limits. New behaviours (remote search, recents, slash-commands, “create new”) are added by registering another source — no change to the widget.
  query ("acce") ─┐
                  ▼
        ┌──────────────────────┐
        │   CompletionEngine   │  debounce · cancel · merge · rank · limit
        └──────────┬───────────┘
       ┌───────────┼───────────┬───────────────┐
       ▼           ▼           ▼               ▼
  StaticSource RecentSource RemoteSource   CreateSource
  in-memory    MRU cache    async/await     "add new"
  fuzzy match  recency rank  cancellable     fallback row
       └───────────┴───────────┴───────────────┘
                  each yields CompletionItem[]

Source & item contract

# A completion source is anything implementing one method.
# The engine merges results from all registered sources.

interface CompletionSource:
    name: str                 # shown in popup header / grouping
    priority: int             # merge/rank order across sources
    async def query(text, context) -> CompletionItem[]

interface CompletionItem:
    value:     str            # committed when chosen
    label:     str            # display text (defaults to value)
    icon:      glyph?         # leading cell
    matches:   (int,int)[]    # char spans to bold-highlight
    meta:      str?           # right-aligned (count, hint, type)
    group:     str?           # section header to file under
    kind:      enum           # tag | recent | create | command
    disabled:  bool           # shown but not selectable (e.g. already added)
    onCommit:  fn?            # override: run instead of inserting a chip

# Register sources in any combination — order = priority:
editor.use([
    StaticSource(tags, match="fuzzy"),
    RecentSource(max=5),
    RemoteSource("/api/tags", debounce=150),
    CreateSource(),          # always last: "Create \"x\""
])
One small method per source, one flat item shape. The matches spans drive the bold highlighting; group files an item under a section header; kind lets a single popup mix tags, recents, and commands; disabled shows-but-blocks (e.g. already-added); onCommit lets an item run an action instead of inserting a chip. Sources are ordered by priority and fully independent.
