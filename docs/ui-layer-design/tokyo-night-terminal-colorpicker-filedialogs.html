▸ Keyboard interaction — breadcrumb navigation & path edit mode

The dialogs above show the breadcrumb's states but not how a keyboard user moves between them. This section specifies that completely: the focus-state machine, how to enter and leave path-edit mode, the completion popup's keys, and the dialog-wide tab-stop model. It composes with the framework's retaining / non-retaining focus scopes — the dialog retains focus; the breadcrumb, its completion popup, and any sibling dropdown are transient scopes layered over it. Bindings marked [CAP] require caps-kitty-keyboard; each has an always-available ungated equivalent — see the Ctrl-chord hazard note below.

Focus-state machine

  breadcrumb focus states — Esc unwinds exactly one level per press

     S0 unfocused
      │  Tab into region  /  F4 · Alt+D (jump straight to S2)
      ▼
     S1 CHIP mode        segments as chips; ←/→ moves the active chip
      │  F4 · Alt+D · F2          ▲ Esc (revert, discard edits)
      ▼                                    │
     S2 EDIT mode        raw path text + caret; path pre-selected
      │  ↓ · Ctrl+Space · Tab(if completable)   ▲ Esc (close popup, keep text)
      ▼                                    │
     S3 EDIT + completion popup open

  and at the dialog's top level:
     S1 Esc ──▶ focus returns to the file list  (NOT dialog-cancel)
     file list Esc ──▶ Cancel the dialog        (final rung)
⚠ Esc MUST UNWIND ONE LEVEL — NOT CANCEL THE DIALOG
The breadcrumb stacks up to three scopes (chips → edit → completion popup). Esc pops exactly one per press, per the framework's focus-scope model. Critically, Esc from the breadcrumb in chip mode returns focus to the file list — it does not cancel the dialog. A user backing out of the path bar must never destroy their dialog. Esc only cancels once focus is already at the dialog's top level with no sub-scope active. The dialog itself is the retaining scope; the breadcrumb, its popup, and the sibling dropdown are non-retaining scopes layered over it — so backing out of them simply falls through to where focus already was.

Entering path-edit mode

Two accelerators, both landing in EDIT mode with the whole path pre-selected so typing replaces it: F4 — the primary, being both the classic address-bar key and the combobox-drop key (apt, because a breadcrumb with completion is a combobox) — and Alt+D (“focus address”). Both work from anywhere in the dialog. With the breadcrumb already focused in chip mode, F2 also enters edit mode (the rename/edit idiom). Pointer users click the path bar's empty space, as shown above.

Deliberately not Ctrl+L. In a browser that means “focus the location bar,” but in a terminal Ctrl+L is the near-universal clear / force-repaint binding (readline's clear-screen; shells, less, vim, tmux), and the framework reserves it app-wide. A dialog stealing it would strand a user hitting Ctrl+L to fix a corrupted screen — exactly when they most need it. Terminal conventions outrank GUI conventions in a terminal app.

RESOLVING THE Tab CONFLICT
Tab means complete in a path field and next region everywhere else in the dialog. The rule that removes the ambiguity — and matches shells and Claude Code — is to make it context-sensitive:
 • popup open → Tab accepts the selected candidate (stays in edit)
 • popup closed, a completion exists for the partial segment → Tab opens the popup / completes the longest common prefix
 • popup closed, nothing to complete (empty partial, or path already exact) → Tab leaves the region, normal tab-stop behavior
The user is never trapped: when there's nothing to complete, Tab does the ordinary thing. And Shift+Tab always leaves, never completes, so there is always an unambiguous way backwards.

⚠ THE Ctrl+<letter> HAZARD IN A TUI
Ctrl-chords map onto ASCII control characters, a space the terminal and shell already own. Three distinct traps, all of which bit this keymap:
1 · Reserved by the terminal layer. Ctrl+C Ctrl+D Ctrl+Z Ctrl+L Ctrl+\ are claimed by shells/terminals. Ctrl+S/Ctrl+Q are XON/XOFF flow control — on terminals where that is still enabled, binding them will freeze your application. Readline also owns Ctrl+R (reverse-search), Ctrl+E (end-of-line), Ctrl+F (forward-char), and many more.
2 · Some are not distinct keys at all. Ctrl+I is Tab. Ctrl+M is Enter. Ctrl+H is Backspace. Ctrl+[ is Esc. These are the same byte — not a conflict you can resolve, a fact of the encoding.
3 · Modifier combinations may be invisible. Ctrl+Enter, Ctrl+Shift+N, Ctrl+Space can only be told apart from their base keys where the terminal reports disambiguated key events — i.e. under caps-kitty-keyboard.
Design rules that follow: prefer function keys and Alt-chords for application accelerators (neither collides with the control-character space). Treat every Ctrl+<letter> binding as capability-gated territory, marked [CAP] above. And critically — no command may be reachable only through a gated binding: every [CAP] shortcut in this keymap has an always-available ungated twin (↓ for the popup, Alt+Enter for commit-as-typed, Alt+N for new folder). This is the keyboard analogue of the whole-cell discipline: respect what the medium already claims.
WHY THE BREADCRUMB IS ONE TAB STOP
A breadcrumb is a container of related, individually-activatable items — structurally the same as a toolbar. Making each segment its own tab stop would tax every keyboard user crossing the dialog (a deep path costs a dozen Tab presses to pass). So it takes the “once” tab stop + arrow navigation rule: Tab treats the whole breadcrumb as one stop; ←→ move within it. The same rule applies to the nav buttons, the view switcher, the places rail, and the file list.
